## Rules

- Her own user: daemons run only from /usr/local/estia as _estia; the checkout is a source, never run. Code there is root:wheel 0755 (`releases/<UTC stamp>-<git sha>`, `current`, `bin/estia`, `bin/estia-deploy`, `tools/`); her data is in `/var/estia` (0700/0600: `.config/local-assistant`, `Library/Application Support/local-assistant`, `.local/share/signal-cli`, `Library/Logs/local-assistant` for `bridge.log`, the voice caches); her services' output (`launchd.log`, `voice.log`) is in `/var/log/estia` (`ownuser.STREAM_LOGS`: root's, 0755; the files hers, 0600, made by `make_stream_logs` before each switch, no link followed; a name that is not her regular file with one name (her account may `ln` it from her home: the same volume) is unlinked and made fresh, never refused, so her account cannot stop an update), which `plist_problem` requires; every path in code follows `$HOME` (`config.CODE_ROOT` is the code's own folder). Root runs only `/usr/local/estia/tools` (its own Python, `deploy`, `ownuser`, `hostsec`, the service templates, `scripts/estia`, `scripts/estia-deploy`: `deploy.TOOL_FILES`), installed with the first release (a retried move installs its own release's again: it runs the checkout as root anyway) and changed only by `estia-deploy --update-tools` after their diff; never a release, never the checkout. Everything she runs is root's: her signal-cli (`vendor/signal-cli-native`, `config.default_signal_cli`), a JDK for the JVM build (`vendor/openjdk.jdk`, `Config.java_home`), the call helpers, and a PATH of `current/.venv/bin:/usr/bin:/bin:/usr/sbin:/sbin` (no Homebrew: its folders are the owner's); doctor's "Her programs" line checks each up to `/`. A service file is rendered from the tools' templates and checked by `ownuser.plist_problem` (her user, programs under `current`, `HOME`, `CFFIXED_USER_HOME`, `PATH`, `LANG`, `PYTHONUNBUFFERED` only, no other keys; her home is given explicitly, since her account record keeps `/var/empty`: also `-Duser.home` in `JAVA_OPTS` and signal-cli's `--config`). Whether she runs as her own user is `ownuser.moved` (the bridge's service file says `_estia`, no rollback on record; `moved()` in `scripts/own-user.sh`), never whether `bin/estia` exists. Docs name `/usr/bin/sudo /usr/local/estia/bin/estia …` in full, never a bare sudo or a bare estia: a planted `sudo` earlier on the owner's PATH catches the password, a planted `estia` would run as root. So does every command code prints or a script echoes (`ownuser.ESTIA`, `DEPLOY_CMD`; `tests/test_docs.py` scans `src/` and the scripts), and the owner's scripts run it by that path: `"$sudo"` from `scripts/own-user.sh` (`$ESTIA_TEST_ROOT/usr/bin/sudo`: under a test's fake tree, its stub), never a bare `sudo`, which would also get the key piped into it.
- The move (`ownuser.Migration`): a preflight (first `hostsec.strays` over her folders: no link out of them, top folder and a folder on the way included, and no FIFO, socket or device, each named, and with one nothing of hers is read (a link made after the walk, before the reads below, is caught by the walk of her copy: they yield only her number, capped, `CONFIG_LIMIT`, and a yes or no); then config, her Signal account (`hostsec.signal_account`, the one reader doctor and setup share too: `read_json`, no link at the name followed, no FIFO waited on, a regular file only, the account file by signal-cli's own name, never a path), the voice build and disk) and the release build come before anything stops; her copy in `/var/estia` is walked again the same way before anything of hers starts; her data is read by the owner (`tar` as the owner) and written by her (`tar` as `_estia`), so root never follows the owner's links; the old folders with secrets are renamed into `/usr/local/estia/rollback/data` (0700, root only), never re-owned in place; any failure, a Ctrl-C or a hang-up (`interruptions_raise`) restores her. The restore and the rollback ignore hang-ups, TERMs and Ctrl-Cs (`interruptions_ignored`) and print each folder still held as two exact lines: root moves it straight into the owner's home under a fresh name (`/usr/bin/sudo /bin/mv -h <held> <home>/estia-restore-<path>-<time>`: no folder on the way, no link followed), then the owner moves it into place without sudo (`_left_over`). The restore puts her old service files back and bootstraps them in a `finally` (`_bring_back`). The rollback renames the held folders back and copies what she saved since on top, as the owner (never the old Signal sessions alone: they would break decryption), after removing the `-wal` and `-shm` next to each `account.db` and `assistant.db` it replaces (as the owner: SQLite replays a stale `-wal` into whatever database sits next to it); every step of that copy that fails raises (`_overlay`), and then her own services start again (`_start_again`), never the owner's old ones, the marker is not written and the success line never printed. Her data never holds a program (an execute bit), a link out of her home, a FIFO or a device (`_overlay_problems`): the rollback refuses one before anything stops (exit 1, she keeps running, each named with its fix as her: `/usr/bin/sudo -u _estia /bin/chmod a-x --` or `/bin/rm --`); a failed move after she ran makes each harmless as her first (`_defuse`), then copies. Once she is moved, `scripts/migrate-to-own-user.sh` stops before any sudo (it would run the checkout as root) and doctor's fixes never name it. `data_modes` shows ✗ for a link out of her folders, with no chmod offered for it. Her helper's output in harden (`--her-checks`) is data only (`harden.her_check`): a state, a text and folder names from a fixed list; the fix is code's own, run as her.
- The move and her config (`ownuser.config_notes`, `_copy_data`): an `avatar` that names a regular file in the owner's home (not a link; `stat` as the owner; no `..`, and no link on the way: `/bin/realpath` as the owner), at most 5 MB, is read as the owner (`head`, within `AVATAR_SECONDS`: a blocked reader is killed, `Host.pipe(timeout=…)`) and written as her (`tee`) into her config folder as `avatar.png`/`.jpg`/`.jpeg` (any other ending: `avatar`; 0600; a file at that name removed first, a copy that changed while read removed), and her config points at it; otherwise her config keeps the path, with a note when it is in the owner's home. `[health] watch_logs` folders in the owner's home are left out of her copy, counted in a note (one-line and multi-line lists). Notes name keys, never values. A successful real move (after the live health check) deletes every release other than `current` (real folders only, `lstat`; never without a `current` that names a folder in `releases/`; never on a failure, in a dry run or a rehearsal) and says how many and the space freed (`human_size`, decimal units), then lists her copies kept aside with `/usr/bin/sudo /usr/local/estia/bin/estia remove-old`. `remove-old` (root, from the tools) deletes the held folders when on record and every direct child of her home named `.before-YYYYMMDD-HHMMSS` that is a real folder (`kept_aside`: `lstat`, a link is never one), also without a move on record, each through `delete_tree` (Python's link-safe `rmtree`) and named; nothing to delete is "No old copies on record", exit 1.
- The nuclear option (`scripts/harden.sh --nuclear`): the firewall (its question names each program that listens for other machines now, keeps the keep-listening questions and says doctor names new ones later), stealth mode (its own question, default no), python3 and ruby off the firewall's list, and the keychain lock, after saying first, plainly, that they may stop other services on this Mac (`harden.NUCLEAR_WARNING`: programs other machines reach stop answering them unless allowed, no answer to ping, more keychain prompts). Without it they are never a "!" or a "✗", in harden or in doctor: harden shows one neutral line (○, `hostsec.NUCLEAR_LINE`), and doctor's firewall line (`hostsec.doctor_firewall`) is ✓ when it is on and that neutral line when it is off or cannot be read. Nothing turns any of them off again: a Mac keeps what it already has. The Mac's security has two levels, by name in every text a person reads (harden, doctor, setup, the docs; never "default"): hardened (setup's security step: SSH with keys only or Remote Login off, her files private, her Registration Lock, and no sudo rule or setting that skips the owner's password, and no sudo sign-in that lasts longer than 5 minutes or never ends (`timestamp_timeout`, `hostsec.SUDO_MINUTES`), wherever it can be read (root's `/usr/bin/sudo -n -l -U <owner>` that `estia doctor` hands her doctor on stdin, `ESTIA_OWNER_SUDO`, and harden once sudo is asked; doctor as the owner, before her own user, reads the rules alone, `owner_sudo`: sudo lists the sign-in settings only after the password or with a rule that skips it; never her bridge's own reading; each command-specific `timestamp_timeout` counts on its own), as doctor reads them, `hostsec.level_checks`) and nuclear (that, the firewall on and no interpreter allowed on its list, `firewall_apps`; stealth mode and the keychain lock never count: the keychain is the owner's, unreadable as her); `hostsec.security_level` gives "" when one of the hardened three was read and does not hold, None when one could not be read (`Check.unread`; her list shows "not read yet", never "not hardened yet"). Doctor's last security line names it (`level_check`: ✓ either level, ! "not hardened yet" naming what is missing, ! "not read" naming what could not be read); harden says its level first (`harden.LEVEL_HARDENED`, `LEVEL_NUCLEAR`) and ends with the doctor command that names the level reached.
- Doctor's firewall lines (`hostsec.firewall_listeners`, read-only, fixed argv, no shell; nothing changes the firewall): with the firewall on and its list readable, each program that listens for other machines and that the firewall does not let through gets a "!" line, never ✗: not allowed on `socketfilterfw --listapps` (paths compared with links resolved, `Host.real_path`, live Mac only; an `.app` covers the programs inside it) and ad-hoc signed or unsigned (`codesign -dvv`) while "allow signed software" is on; one blocked on the list whatever its signature; with allow-signed off, a signed one not on the list too. Block all incoming connections (`State = 2` or `--getblockall`) gives one line naming every listener with `--setblockall off`, no per-program commands. A signature codesign cannot read gives no line; a listener whose program is not found, or whose path has control characters, gets a "may not be reachable" line with `/usr/bin/sudo /usr/sbin/lsof -nP -iTCP:<port> -sTCP:LISTEN` (no System Settings: a Mac without a screen). Names and paths are printed without control characters (`_printable`). The fix is "if you started it and other machines should reach it:" and the two commands `/usr/bin/sudo /usr/libexec/ApplicationFirewall/socketfilterfw --add <path>` and `--unblockapp <path>`, the path shell-quoted; a program under `/tmp` or `/var/folders` gets no command. The Registration Lock ✓ line says to keep the PIN in a password manager.

## Gotchas

- The venv is not relocatable and uv's Python lives in the owner's home (0700 for `_estia`): a release holds its own interpreter and builds its editable `.venv` at its final path (code finds its files through `Path(__file__).parents[2]`).
- launchd opens `StandardOutPath` and `StandardErrorPath` for appending: emptying the file (ftruncate) is enough, writing goes on at its new end. It opens them as root, so they live in `/var/log/estia`, a folder only root can change: no link of hers is ever followed there (an install from before keeps them in her folder, where a program of her account could make root write into a file it names, until `--update-tools` and one more deploy: doctor's ✗ Services, a known gap in SECURITY.md until then; the docs' update order is deploy, `--update-tools`, deploy again).
- A deploy's health check counts only a new bridge process with `last_alive` after the restart (`Deploy.health(restarted, old_pid)`): the old bridge keeps writing it during the minutes the build takes.
- The freeze keeps each file's times (`os.utime`): the bytecode `uv sync` and `compileall` wrote checks them, and her user cannot write `__pycache__` in the release.
- A team ID is a claim, not a proof: a copy of `/usr/bin/true` signed ad hoc with `codesign -s - --team-identifier 3MU9H2V9Y9` passes `codesign --verify --strict` and `codesign -dv` prints `TeamIdentifier=3MU9H2V9Y9` (`Signature=adhoc`; live 15 Oct). Only a requirement proves Apple's chain: `codesign --verify --strict -R '=anchor apple generic and certificate 1[field.1.2.840.113635.100.6.2.6] exists and certificate leaf[field.1.2.840.113635.100.6.1.13] exists and certificate leaf[subject.OU] = "3MU9H2V9Y9"'` (exit 3 for the forged copy; every program, library and metallib of Ollama's v0.40.4 passes, metallibs included, 15 Oct).
- A link check by its text is not enough: `sub/b -> ..`, `b -> .` and `b/b/../../..` leave the tree after the kernel follows the links; `deploy._check_links` and doctor's code check use `realpath`. Root opens build files with `O_NONBLOCK` (a FIFO swapped in must not hang it).
- The owner's `sudo` from a Claude Code `!` command has no terminal for the password: every sudo command goes in the person's own Terminal window.
- Ollama picks Gemma 4's prompt by the model's name (e2b, e4b: small; 12b, 26b, 31b: large; Ollama 0.40.4, `server/renderer_resolution.go`), and the alias `local-worker` names no size: it got the prompt for the small models, without the empty thought block Google's prompt for 12B and larger ends with when thinking is off, and about 1 answer in 10 came back empty (11 to 17 Oct; the likely cause, by elimination). The alias's Modelfile names `RENDERER gemma4-large` for a Gemma 4 tag of 12B or more (`setup.modelfile`, `ollama_build.large_gemma4`); a smaller Gemma 4 keeps Ollama's pick. An alias made before 0.9.3 keeps the small prompt until it is made again: doctor's "Model prompt" line reads the model's Modelfile and size from `/api/show` (POST, read-only; `ollama_build.gets_small_prompt`, Ollama 0.40.4's rule), and setup's model step on a re-run asks, then makes it again from its own model (`Wizard.alias_base`, only while that -mlx tag has its tested digest: the tag whose digest it has, a copy, else the tag it holds with at most a num_ctx of its own, `setup.made_from`: the same architecture, parameter count, format and quantization, template, system prompt and parameters but num_ctx, from each `/api/show`, and a size in `/api/tags` within `ALIAS_EXTRA_BYTES`; Ollama names no parent for an MLX build, `parent_model` "", so setup's own aliases have only that) with its own context (`Wizard.remake`); the digest changes, so a pin pauses answers until `model_digest` has the new one (setup prints it).
