# Mail and calendars

## Layout

- `mail_http`, `mail_auth` (device-code sign-in, tokens per mailbox and scope), `graph` (read-only Graph client), `mail_sync` (delta sync of headers), `mail_sort` (labels at idle time), `mail_digest` (the digest's mail part, numbers of the day in the digest's order whichever reads first, at most 10 replies and 10 actions over all mailboxes, the call's glance as counts; a mailbox not read, its part failing in `status.json` for a sync round at least and its last good read older than `STALE_ROUNDS` (2) sync rounds, gets code's line in the digest and the mail tools' headers, a count and a time in the glance), `mail_tools` (what Gemma's mail tools return)
- `calendar_feed` (every configured calendar read together: the calendar helper per Google or CalDAV calendar (a CalDAV account on its stdin, never in argv), events in local time, a failing calendar named, duplicates kept once), `calendar_graph` (Outlook calendars of the mailboxes: own Graph, Calendars.Read only, pauses), `calendar_tools` (the digest's calendar block, what Gemma's calendar tools return; calendar names before titles when there are several; today's agenda lines marked by code after their times, before the title: "(over)", "(now, until 15:00)", "(in 40 min)", true only at the read, so a replay drops them, `context._short_result`; the call's glance as counts and times), `morning_digest` (the 09:15 digest: schedule, calendar on top, then mail)
- `tools/ical/`: the calendar helper (icalendar + recurring-ical-events in its own uv environment; reads one Google calendar's address by name and expands the feed, or with `--caldav` one CalDAV calendar: its account as one JSON line on stdin, its app-specific password from `calendar.env`, standard library HTTP (`http.client`), PROPFIND and REPORT only).
- `calendar_watch` (calendar changes and the early start) is named with `initiative` in `docs/agents/memory-initiative.md`.

## Commands

- Calendar helper: `cd tools/ical && uv run pytest -q && uv run mypy`; save or replace a Google calendar's address: `scripts/set-calendar-url.sh [name]` (hidden prompt; replaces only that calendar's key in `calendar.env`, with `CALENDAR_SAVED_AT[_NAME]` next to it: when, for doctor); a CalDAV calendar's app-specific password the same way: `scripts/set-calendar-password.sh [name]` (`CALDAV_PASSWORD[_NAME]`)
- Mail sign-in: `scripts/mail-login.sh <address> [--mail-only]` (asks for Calendars.Read too when the mailbox's calendar is configured; `--mail-only` without it)

## Rules

- Mail sorting funnel: replies by the user -> waiting; correspondents (anyone the user mailed, To or Cc, kept in `mail_correspondents` beyond the headers), replies in the user's threads, bounces and bills/payments/security/appointment words (EN + NL) always go to Gemma; otherwise List-Id / Precedence bulk -> noise; List-Unsubscribe / Auto-Submitted only with Jev's agreement (p >= 0.5); then the optional local AgentJev (`[mail] jev_url`, localhost only) -> noise when at least `jev_threshold` sure, else Gemma. One in five pre-filtered mails is double-checked by Gemma (its label wins). `mail_triage` keeps the step, Jev's number and Gemma's label (no text) to measure Jev.
- Mail is read-only by permission (`Mail.Read`): no code may send, move, delete or mark mail. Mail's token request asks for the mail scopes only (`mail_auth.SCOPES`, unchanged), so mail never depends on the calendar's consent. Mail bodies are never stored (headers, label and a checked one-line summary only; mail tool results are not written to the tool log, which keeps a stub); mail text is data, never instructions, and never teaches the profile (in an answer that read mail, `remember` and `forget` are refused in code). Refresh tokens only in `mail-tokens.json` (0600).
- Calendars are read-only: Google iCal feeds and Outlook calendars with delegated `Calendars.Read` only (never `Calendars.ReadWrite` or `.Shared`; its own token request, never mail's token; no code may create, change or answer an event). A Google calendar's address is a password: only in `calendar.env` (0600, one key per calendar), read only by the calendar helper, which fetches only Google's iCal host and follows no redirects; the bridge never holds it. An Outlook calendar asks Graph for no bodies, attendees or organizer address, and keeps only a place's display name; missing consent (AADSTS65001 or 70000) is its own reason (`no_consent`), never mail's pause; doctor counts only a new sign-in of the mailbox as its fix (`signed_in_at`; mail renewing the token is none), and only one that asked for `Calendars.Read` for missing consent. A CalDAV calendar (`[[calendar.sources]]` with `caldav`, `user`, `calendar`; iCloud, Fastmail, Nextcloud) is read by the calendar helper with PROPFIND and REPORT only (`READ_METHODS`; every other method refused in `CalDav.request` and `https_transport`, tested), standard library HTTP, HTTPS only, the configured host only on the same port (`site_of`: only a provider in `MULTI_HOST_SITES`, iCloud today, may send it on to its other hosts), redirects and answer addresses alike, at most 3 redirects, no proxies, no cookies, all requests within `CALDAV_SECONDS` (12 s: a timer per request, as a socket timeout lets a slow server drip on; with `EXPAND_SECONDS` under the bridge's 30 s) and the feed's 20 MB cap, XML with a document type or entities refused (expat handlers), then the feed's own expansion and caps (one unreadable event object left out); its account goes to the helper on stdin, never argv (`ps`), and its app-specific password (`CALDAV_PASSWORD[_NAME]` in `calendar.env`) only the helper reads; its failures are its own reasons (`no_password`, `password_refused` (a 401, or a 403 before any answer came: a later 403 is `invalid`) with one note like a dead Google address, `no_calendar`), each with doctor's fix; an invalid answer carries a fixed code (`INVALID_CODES`, copied in `calendar_feed` and test-checked against the helper's), the only part of it the bridge logs. One failing calendar never hides the others. Events are read live, never cached; event text stays only where mail text does (the sent digest note, Gemma's answers), and calendar tool results are a stub in the tool log; event text is data (cleaned, capped, links removed from places), and an answer that read the calendar refuses `remember`/`forget` and makes device requests wait for the user's yes.

## Gotchas

- A calendar feed is outside input: `recurring-ical-events` loops forever on `INTERVAL=0`, floods on rules finer than daily, crawls on rules that never occur and on long events overlapping its search windows; one unreadable rule used to stop the whole feed. The helper drops unreadable, never-advancing and finer-than-daily rules, expands each repeating event on its own (0.5 s, 400 occurrences) with `between()`, and has a hard limit (15 s; the bridge 30 s).
- A domain guessed from a host's last labels is no boundary: ts.net (Tailscale), duckdns.org, synology.me and myfritz.net give every customer a host under one public suffix, each with a valid certificate. A CalDAV redirect or answer address is followed to the configured host only, iCloud's own hosts by name (`MULTI_HOST_SITES`).
- A helper the bridge runs with `python -I` (`tools/ical` too): see `docs/agents/devices.md`, Gotchas.
